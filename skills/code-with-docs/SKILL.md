# Code With Docs

## 适用范围与核心目标

- 本技能**只能手动触发**：仅当用户明确使用 `$code-with-docs` 时才执行。不得因为用户提到“需求分析”“写计划”或普通编程请求而隐式启用。
- 本技能的默认产物是经过确认的需求文档和开发计划，而不是代码。目标是在正式编程前，使用户与 AI 对目标、范围、交互、技术方案和验收标准达成一致。
- 不得带着尚未识别或尚未确认的关键疑问进入代码编写。不能用“先写出来再看”的方式代替需求对齐。
- 即使用户在首次消息中同时要求“分析并开发”，也必须先完成文档前置流程；文档就绪后暂停，等待用户在后续消息中明确下达开发指令。

## 总体工作流

按以下顺序执行，不得跳过需求确认和文档落盘阶段：

1. **了解项目上下文** -> verify: 已读取适用的仓库指令，并检查现有文档、目录结构和必要的项目实现。
2. **逐项对齐需求** -> verify: 关键决策均有明确结论；未决问题已被提出，不再隐藏假设。
3. **增量维护 `docs/prd/`** -> verify: 每个已确认的需求和设计点都已经写入 PRD。
4. **基于 PRD 进行开发设计** -> verify: 技术选型、复用策略、改动边界、实施顺序和验证方式均已明确。
5. **维护 `docs/plans/` 并请求确认** -> verify: 开发计划引用对应 PRD，且没有与 PRD 冲突的内容。
6. **宣布就绪并停下** -> verify: 已告知用户文档路径和状态，未在本技能的文档阶段修改业务代码或开始开发服务。
7. **收到后续明确开发指令后才实现** -> verify: 编码严格依据已确认文档；遇到新的关键歧义时先停下对齐并更新文档。

## 阶段 0：进入前的项目检查

启用技能后，先做与当前任务相关的最小检查：

- 遵循仓库根目录及相关子目录中的 `AGENTS.md`、`CLAUDE.md` 等指令；`sove-skills` 是始终生效的基线。
- 检查 `docs/prd/`、`docs/plans/` 是否存在及其中已有文档，识别正在进行的需求、已确认内容和用户已有修改。不要覆盖或重写无关文档。
- 按需检查 README、包管理文件、配置文件、现有模块和相邻功能实现，以了解项目实际边界、依赖、代码风格和可复用能力。不要仅凭通用经验猜测项目技术栈。
- 文档目录不存在时，可以创建 `docs/prd/` 和 `docs/plans/`；仅创建完成当前流程所需的目录和文件。
- 文档阶段不得启动、重启或停止开发服务器、数据库、容器或其他持久服务。

## 阶段 1：需求对齐与反向提问

### 提问规则

- 只要目标、范围、用户角色、关键行为、数据、权限、安全、兼容性、异常处理或验收标准存在实质性不确定，就必须向用户提问，不能自行补全。
- 一次只问**一个问题**。每个问题提供多个带编号的可选方案，明确标出一个推荐方案，并用一句话说明推荐理由。
- 必须等待当前问题得到用户明确且前后一致的确认后，才能继续下一个问题。若用户回答含糊、互相矛盾或与已有决定冲突，应留在当前问题继续澄清。
- 已由仓库、已有 PRD 或用户明确说明的事实不要重复提问；低风险且不影响范围、行为、兼容性或架构的细节可采用项目既有惯例。
- 每次确认后立即把结论写入 PRD，避免只存在于对话记忆中。对尚未确认的内容标记为“待确认”，不得写成既定事实。

### 建议覆盖的决策面

根据任务选择必要的问题，至少确保以下适用项有结论：

- 背景、要解决的问题、目标用户和使用场景；
- 本次目标、非目标、范围边界、优先级和成功指标；
- 核心用户流程、页面/交互状态、输入输出和反馈；
- 数据实体、字段含义、数据来源、生命周期、持久化和迁移影响；
- API、事件、第三方服务、权限角色、认证、隐私和安全要求；
- 空状态、加载态、失败重试、校验、并发、边界条件和异常提示；
- 浏览器、设备、运行环境、版本兼容性、国际化和无障碍要求；
- 验收标准、测试重点、上线约束、风险和明确不做的事项。

### 需求状态管理

在文档中区分以下状态，不能混用：

- **已确认**：用户明确同意，或已有项目事实明确证明；
- **假设**：为推进讨论暂时采用，必须显式标注并在进入开发前确认或废弃；
- **待确认**：会影响实现或验收，必须继续提问；
- **已否决/非目标**：明确不纳入本次范围，避免后续误实现。

当需求无法安全实现或多个方案会导致明显不同的成本、行为或架构时，先展示选项与推荐，再等待用户决定。不要用沉默的默认值掩盖不确定性。

## 阶段 2：PRD 文档（`docs/prd/`）

### 创建、更新与命名

- PRD 是项目需求与产品设计的事实来源。需求讨论中确认的点要逐步、一一落盘到这里，而不是等全部讨论结束后凭记忆一次性补写。
- 修改已有 PRD 前先阅读相关内容，保留用户或其他开发者已有结论；若新结论改变旧结论，记录变更原因和影响，不要静默覆盖。
- 文件名使用：`前置序号-小写英文短横线名称.md`；拆分时使用：`前置序号-小写英文短横线名称-章节序号.md`。推荐序号使用两位数字，例如 `01-user-auth.md`、`02-order-flow-01.md`。
- 前置序号按目标目录中现有文件的最大前置序号递增；即使目录中只有 `05-...`，下一个也从 `06` 开始，目录为空时从 `01` 开始。不得因首字母排序而重新编号已有文件。
- 后置章节序号仅在同一主题拆分为多篇时使用，并按逻辑顺序递增，如 `02-order-flow-01.md`、`02-order-flow-02.md`。单篇文档不必添加后置序号。
- 若文档过大、主题边界清晰或多个章节会独立演进，应主动拆分；不要为了凑篇数无意义拆分，也不要把多个独立需求塞进一个超长文件。

### PRD 最小内容结构

根据任务裁剪，但应覆盖所有适用内容：

1. 文档元信息：标题、状态、关联文档、最后确认范围；
2. 背景与问题：为什么做、解决谁的什么问题；
3. 目标与非目标：可观察的目标、明确不做的内容；
4. 用户与场景：角色、前置条件、主要使用路径；
5. 功能需求：按编号描述行为、规则、输入、输出和优先级；
6. 交互与状态：页面/组件状态、流程、提示、空状态和错误状态；
7. 数据与外部约束：实体、字段、来源、接口、权限、合规和兼容性；
8. 验收标准：可验证、可复现、与需求逐项对应的条件；
9. 决策记录：已确认、假设、待确认、已否决项及其原因。

需求描述应优先使用清晰的自然语言、表格、流程和验收条件；不要在 PRD 中堆积实现代码或未经确认的技术细节。

## 阶段 3：开发设计与计划（`docs/plans/`）

### 进入条件

- 只有在影响实现的 PRD 关键项已确认、目标和验收标准清晰、待确认项已清零或被用户明确接受为后续事项后，才能编写最终开发计划。
- 在从需求转入技术设计前，先检查已有代码和依赖，特别是相邻功能、公共组件、工具函数、状态管理、接口层、样式规范和测试组织方式。
- 若 PRD 本身仍存在阻塞性问题，继续反向提问，不得用开发计划掩盖需求缺口。

### 技术设计要求

开发计划必须说明“怎么做”和“为什么这样做”，至少包括：

- 总体实现思路、模块/目录/文件影响范围和不应触碰的边界；
- 现有能力的复用点，以及确实需要新增的抽象、组件、工具或依赖；
- 技术栈和关键库的选型、版本/兼容性约束、备选方案与取舍理由；
- 数据模型、API/事件契约、状态流转、权限边界和错误处理策略；
- 与现有代码风格、架构、命名、目录组织和测试方式保持一致的具体要求；
- 按依赖关系排列的实施步骤，每一步的输入、输出和完成判据；
- 迁移、回滚、配置、发布或数据兼容影响（适用时）；
- 测试与验证计划：最小必要的单元、集成、端到端、类型、构建或静态检查；
- 风险、未覆盖范围、后续工作和需要在实现中再次确认的条件。

### 计划文档约束

- 计划应让开发者能够直接执行，避免让开发者再次从零分析方案或重新选择技术栈。
- 优先复用项目已有实现；非必要不得引入新依赖、重写已有模块或另起一套风格。需要新增依赖时，说明兼容性、维护性、安全性、许可证、成本和集成复杂度。
- 不要在计划中粘贴大量业务代码示例；仅在解释关键接口或不可替代的用法时保留最小示意。
- 计划中的任务应可检查，包含目标文件/模块、行为变化、依赖关系和验证方式，不写“完善一下”“按需处理”等不可执行表述。
- 计划文件也遵循同一套序号和命名规则，序号在 `docs/plans/` 内独立递增，例如 `01-user-auth-plan.md`。拆分时使用 `01-user-auth-plan-01.md` 等后置章节序号。
- 计划必须链接或明确引用对应 PRD；若实现过程中需求变更，先回写 PRD，再同步更新计划，禁止只改计划不改需求事实来源。

## 阶段 4：就绪门禁与后续实现

### 文档确认门禁

完成 PRD 和开发计划后，向用户汇报：

- 已创建或更新的 PRD 和计划文件路径；
- 已确认的目标、范围、关键设计和技术选型；
- 已解决的问题、仍保留的非阻塞事项及其状态；
- 计划的实施边界和最小验证范围。
- **最后一次测试验证制度确认**：在宣布文档前置工作完成前，必须向用户单独提问：“是否禁止 AI 进行测试脚本编写和对程序进行测试验证？”并提供以下选项：
  1. **禁止 AI 进行测试验证的过程**：AI 只需要写代码，一切测试和验证皆由开发者本人手动完成；AI 在写完代码之后可以向开发者提供测试验证的建议步骤，但不允许代替开发者直接进行任何测试验证行为。该选择同时禁止 AI 编写测试脚本。
  2. **保持现有测试制度不变**：继续遵循本技能及项目既有的测试与验证规则。

必须等待用户明确选择上述选项。获得选择后，立即将结论以“已确认”状态归档到开发计划中；如该选择影响 PRD 中的验收标准、测试重点或决策记录，则同步更新 PRD。不得只保留在对话记忆中，也不得在归档完成前宣布文档前置工作完成。

然后明确告知“文档前置工作已完成，可以开始开发”，并**停止执行，等待用户下一条明确的开发授权**。没有这条后续授权，不得修改业务代码、生成实现文件、运行会改变项目状态的脚本或启动服务。

“看起来可以”“继续”“按这个来”等只有在上下文明确指向开始编码时，才可视为开发授权；对仍有歧义的短回复应先确认含义。

### 获得开发授权后

- 实现前再次阅读对应 PRD 和计划，并按计划逐项执行；遵循项目已有代码风格，先复用后新增。
- 任何超出文档、改变公共契约、影响数据/权限/兼容性的发现，都必须暂停实现，向用户一次提出一个澄清问题，并先更新 PRD/计划再继续。
- 不得静默扩大范围、改变已确认行为、以临时实现代替未决设计，或把未验证的推断写进代码。
- 实现完成后按计划执行最小且足够的验证，准确报告已执行、跳过、阻塞和失败的检查；不得声称未运行的检查已通过。

## 禁止事项

- 禁止隐式触发本技能或绕过文档流程直接编码。
- 禁止在关键需求未确认时自行拍板，禁止把假设写成已确认需求。
- 禁止只在聊天中讨论而不把确认结论写入 `docs/prd/` 或 `docs/plans/`。
- 禁止在开发计划中大量复制业务代码，禁止不检查已有实现和依赖就重新造轮子。
- 禁止为了文档完整而添加未经用户确认的功能、技术栈、依赖、架构或验收标准。
- 禁止覆盖无关的既有文档、用户修改或代码；发现冲突时保留原内容并明确报告。

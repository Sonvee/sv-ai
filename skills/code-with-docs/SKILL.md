# Code With Docs

## 适用范围与核心目标

- 本技能**只能手动触发**：仅当用户明确使用 `$code-with-docs` 时才执行。不得因为用户提到“需求分析”“编写规格”或普通编程请求而隐式启用。
- 本技能的默认产物是经过确认的 PRD、按需编写的 ADR 和包含实施清单的 Spec，而不是代码。目标是在正式编程前，使用户与 AI 对目标、范围、交互、技术方案和验收标准达成一致。
- 不得带着尚未识别或尚未确认的关键疑问进入代码编写。不能用“先写出来再看”的方式代替需求对齐。
- 即使用户在首次消息中同时要求“分析并开发”，也必须先完成文档前置流程；文档就绪后暂停，等待用户在后续消息中明确下达开发指令。

## 总体工作流

按以下顺序执行，不得跳过需求确认和文档落盘阶段：

1. **了解项目上下文** -> verify: 已读取适用的仓库指令，并检查现有文档、目录结构和必要的项目实现。
2. **逐项对齐需求** -> verify: 关键决策均有明确结论；未决问题已被提出，不再隐藏假设。
3. **增量维护 `docs/prd/`** -> verify: 每个已确认的需求和产品设计点都已经写入 PRD。
4. **基于 PRD 识别关键技术决策，按需维护 `docs/adr/`** -> verify: 适用的已有 ADR 已引用；必要的新决策已确认并记录；无需 ADR 时有明确判断依据。
5. **基于 PRD 和适用 ADR 维护 `docs/specs/` 并请求确认** -> verify: Spec 明确实现约定、实施清单和验证安排，引用对应 PRD 与适用 ADR，且三者一致。
6. **宣布就绪并停下** -> verify: 已告知用户文档路径和状态，未在本技能的文档阶段修改业务代码或开始开发服务。
7. **收到后续明确开发指令后才实现** -> verify: 编码严格依据已确认文档；遇到新的关键歧义时先停下对齐并更新文档。

### 文档职责

- **PRD**：需求与产品设计的事实来源，说明为什么做、做什么、业务规则和验收标准。
- **ADR**：记录具有架构意义的技术决策，说明为什么选择该方案、替代方案和代价；按需创建，一篇聚焦一个决策。
- **Spec**：本技能中的技术实现规格，说明模块边界、数据与接口契约、状态和异常处理等实现约定，并在文末包含可执行的实施清单。
- 文档按任务规模裁剪，不重复复制其他文档的内容；Spec 通过引用追溯需求和决策。
- PRD → ADR（按需）→ Spec 是主要依赖顺序，允许在细化 Spec 时补充或修订 ADR；若改变需求，先回到 PRD 对齐，再同步相关文档。

## 阶段 0：进入前的项目检查

启用技能后，先做与当前任务相关的最小检查：

- 遵循仓库根目录及相关子目录中的 `AGENTS.md`、`CLAUDE.md` 等指令；`sove-skills` 是始终生效的基线。
- 检查 `docs/prd/`、`docs/adr/`、`docs/specs/` 是否存在及其中已有文档，识别正在进行的需求、已确认内容和用户已有修改。
- 按需检查 README、包管理文件、配置文件、现有模块和相邻功能实现，以了解项目实际边界、依赖、代码风格和可复用能力。不要仅凭通用经验猜测项目技术栈。
- 文档目录不存在时，仅创建当前流程所需的 `docs/prd/`、`docs/specs/`；只有确需新增 ADR 时才创建 `docs/adr/`。
- 文档阶段不得启动、重启或停止开发服务器、数据库、容器或其他持久服务。

## 阶段 1：需求对齐与反向提问

### 提问规则

- 只要目标、范围、用户角色、关键行为、数据、权限、安全、兼容性、异常处理或验收标准存在实质性不确定，就必须向用户提问，不能自行补全。
- 一次只问**一个问题**。每个问题提供多个带编号的可选方案，明确标出一个推荐方案，并用一句话说明推荐理由。
- 必须等待当前问题得到用户明确且前后一致的确认后，才能继续下一个问题。若用户回答含糊、互相矛盾或与已有决定冲突，应留在当前问题继续澄清。
- 已由仓库、已有 PRD 或用户明确说明的事实不要重复提问；低风险且不影响范围、行为、兼容性或架构的细节可采用项目既有惯例。
- 每次准备反向提问前，必须先判断该问题是否确实影响当前需求，以及是否存在过度设计或偏离需求主线的倾向；只有必要且能推动当前需求决策的问题才可提出。不必要、重复、可由上下文或项目惯例确定，或属于低风险细节的问题一律不问；提问应简明，避免把一个决策拆成多个冗余问题。
- 每次确认后立即把需求和产品设计结论写入 PRD；关键技术决策归档到 ADR，具体实现约定归档到 Spec，避免只存在于对话记忆中。对尚未确认的内容标记为“待确认”，不得写成既定事实。

### 建议覆盖的决策面

根据任务选择必要的问题，至少确保以下适用项有结论：

- 背景、要解决的问题、目标用户和使用场景；
- 本次目标、非目标、范围边界、优先级和成功指标；
- 核心用户流程、页面/交互状态、输入输出和反馈；
- 数据实体、字段含义、数据来源、生命周期、持久化和迁移影响；
- API、事件、第三方服务、权限角色、认证、隐私和安全要求；
- 空状态、加载态、失败重试、校验、并发、边界条件和异常提示；
- 浏览器、设备、运行环境、版本兼容性、国际化和无障碍要求；
- 验收标准、测试重点、上线约束、风险和明确不做的事项。

### 需求状态管理

在文档中区分以下状态，不能混用：

- **已确认**：用户明确同意，或已有项目事实明确证明；
- **假设**：为推进讨论暂时采用，必须显式标注并在进入开发前确认或废弃；
- **待确认**：会影响实现或验收，必须继续提问；
- **已否决/非目标**：明确不纳入本次范围，避免后续误实现。

当需求无法安全实现或多个方案会导致明显不同的成本、行为或架构时，先展示选项与推荐，再等待用户决定。不要用沉默的默认值掩盖不确定性。

## 阶段 2：PRD 文档（`docs/prd/`）

### 创建、更新与命名

- PRD 是项目需求与产品设计的事实来源。需求讨论中确认的点要逐步、一一落盘到这里，而不是等全部讨论结束后凭记忆一次性补写。
- 修改已有 PRD 前先阅读相关内容，保留用户或其他开发者已有结论；若新结论改变旧结论，记录变更原因和影响，不要静默覆盖。
- 文件名使用：`前置序号-小写英文短横线名称.md`；拆分时使用：`前置序号-小写英文短横线名称-章节序号.md`。推荐序号使用两位数字，例如 `01-user-auth.md`、`02-order-flow-01.md`。
- 前置序号按目标目录中现有文件的最大前置序号递增；即使目录中只有 `05-...`，下一个也从 `06` 开始，目录为空时从 `01` 开始。不得因首字母排序而重新编号已有文件。
- 后置章节序号仅在同一主题拆分为多篇时使用，并按逻辑顺序递增，如 `02-order-flow-01.md`、`02-order-flow-02.md`。单篇文档不必添加后置序号。
- 若文档过大、主题边界清晰或多个章节会独立演进，应主动拆分；不要为了凑篇数无意义拆分，也不要把多个独立需求塞进一个超长文件。

### PRD 最小内容结构

根据任务裁剪，但应覆盖所有适用内容：

1. 文档元信息：标题、状态、关联文档、最后确认范围；
2. 背景与问题：为什么做、解决谁的什么问题；
3. 目标与非目标：可观察的目标、明确不做的内容；
4. 用户与场景：角色、前置条件、主要使用路径；
5. 功能需求：按编号描述行为、规则、输入、输出和优先级；
6. 交互与状态：页面/组件状态、流程、提示、空状态和错误状态；
7. 数据与外部约束：实体、字段、来源、接口、权限、合规和兼容性；
8. 验收标准：可验证、可复现、与需求逐项对应的条件；
9. 需求与产品决策记录：已确认、假设、待确认、已否决项及其原因；技术决策通过关联 ADR 引用。

需求描述应优先使用清晰的自然语言、表格、流程和验收条件；不要在 PRD 中堆积实现代码或未经确认的技术细节。

## 阶段 3：关键技术决策（`docs/adr/`，按需）

### 进入条件

- 只有在影响实现的 PRD 关键项已确认、目标和验收标准清晰、阻塞性待确认项已解决，其他待确认项被用户明确接受为后续事项后，才能进入技术决策和规格设计。
- 在从需求转入技术设计前，先检查已有代码和依赖，特别是相邻功能、公共组件、工具函数、状态管理、接口层、样式规范和测试组织方式。
- 若 PRD 本身仍存在阻塞性问题，继续反向提问，不得用 ADR 或 Spec 掩盖需求缺口。

### 是否需要 ADR

- 先检查已有 ADR 是否适用，适用时直接引用，不为同一有效决策重复建档。
- 当方案涉及重要的技术栈或依赖选择、模块/系统边界、持久化或通信方式、认证信任边界，或存在显著兼容性、迁移成本和长期约束时，记录 ADR。只记录对当前需求有实际影响的决策。
- 沿用现有架构且没有新的关键取舍的小改动，无需新增 ADR；在 Spec 中说明沿用的约定、适用 ADR，或无需 ADR 的理由，不创建占位文档。
- 需要用户决定的关键取舍，按一次一个问题的规则展示备选方案、推荐和代价，确认后再标为“已接受”。

### ADR 最小内容与维护

1. 元信息：决策标题、状态、日期、对应 PRD 和关联 ADR/Spec（已有时）；
2. 背景与约束：决策解决的问题、相关需求及现有实现限制；
3. 可行选项：适用的备选方案及主要利弊；
4. 决策与理由：选择、排除其他方案的原因；新增依赖时说明兼容性、维护性、安全性、许可证、成本和集成复杂度；
5. 后果：收益、代价、风险、兼容性和迁移影响（适用时）。

- 区分“提议”“已接受”“已否决”“已替代”等状态；最终 Spec 只能以仍适用的“已接受”决策作为实现依据。
- 一篇 ADR 聚焦一个关键决策，不承载完整实现规格或任务清单。沿用阶段 2 的序号和命名规则，序号在 `docs/adr/` 内独立递增，例如 `01-auth-session-storage.md`。
- 已接受的决策被推翻时，新增 ADR 解释替代理由，并在旧 ADR 标明替代关系，保留历史；不要静默重写原决策。

## 阶段 4：技术实现规格与实施清单（`docs/specs/`）

### 进入与完成条件

- 基于已确认的 PRD 和适用 ADR 编写 Spec。细化过程中发现新的关键取舍，先补充或修订 ADR；涉及需求变化时先更新并确认 PRD，再同步 ADR 和 Spec。
- Spec 的状态区分“草稿”和“已确认”；完成时，阻塞实现的需求、技术决策和规格问题均已解决，所引用 ADR 已接受且仍适用，实施清单和验证安排明确。非阻塞后续事项须显式列出，不得纳入当前实现的隐含前提。

### Spec 最小内容结构

根据任务裁剪，但应覆盖所有适用内容：

1. 元信息与依据：标题、状态、对应 PRD、适用 ADR；无 ADR 时说明理由；
2. 实现范围与复用：总体实现思路、模块/目录/文件影响范围、不应触碰的边界、现有复用点和必要新增内容；
3. 实现约定：数据模型、字段与校验、API/事件契约、状态流转、权限边界、错误处理；明确适用的版本/兼容性和项目代码规范；
4. 变更影响：迁移、回滚、配置、发布或数据兼容影响（适用时）；
5. 验收与验证：对应 PRD 需求/验收条目的实现位置及验证方式，最小必要检查和执行责任；
6. 风险与待办：已知风险、未覆盖范围、后续事项和需要重新对齐的触发条件；
7. 实施清单：按依赖关系排列可检查的任务，每项包含目标文件/模块、行为变化、依赖、输入/输出和完成判据，并引用对应验证方式。

### Spec 文档约束

- Spec 应让开发者能够直接执行，避免再次从零分析方案或重新选择技术栈；通过引用 ADR 解释关键选择，不复制完整决策论证。
- 优先复用项目已有实现；非必要不得引入新依赖、重写已有模块或另起一套风格。需要新增依赖时，说明兼容性、维护性、安全性、许可证、成本和集成复杂度。
- 不要在 Spec 中粘贴大量业务代码示例；仅在解释关键接口或不可替代的用法时保留最小示意。
- 实施清单放在 Spec 文末；不写“完善一下”“按需处理”等不可执行表述。小任务保留简短规格和清单即可。
- Spec 文件遵循阶段 2 的序号和命名规则，序号在 `docs/specs/` 内独立递增，例如 `01-user-auth-spec.md`。过大时按主题拆分，如 `01-user-auth-spec-01.md`，通过链接导航，并将实施清单集中在该主题的末篇，避免重复维护。
- Spec 必须链接或明确引用对应 PRD 和适用 ADR；需求、技术决策、实现约定分别在各自文档维护，变化后检查引用和实施清单是否仍一致。

## 阶段 5：就绪门禁与后续实现

### 文档确认门禁

完成 PRD、必要的 ADR 和 Spec 后，向用户汇报：

- 已创建或更新的 PRD、ADR 和 Spec 文件路径，以及复用的 ADR 或无需 ADR 的理由；
- 已确认的目标、范围、关键设计和技术选型；
- 已解决的问题、仍保留的非阻塞事项及其状态；
- Spec 的实施边界、实施清单和最小验证范围。
- **最后一次测试验证制度确认**：在宣布文档前置工作完成前，必须向用户单独提问：“是否禁止 AI 进行测试脚本编写和对程序进行测试验证？”并提供以下选项：
  1. **禁止 AI 进行测试验证的过程**：AI 只需要写代码，一切测试和验证皆由开发者本人手动完成；AI 在写完代码之后可以向开发者提供测试验证的建议步骤，但不允许代替开发者直接进行任何测试验证行为。该选择同时禁止 AI 编写测试脚本。
  2. **保持现有测试制度不变**：继续遵循本技能及项目既有的测试与验证规则。

必须等待用户明确选择上述选项。获得选择后，立即将结论以“已确认”状态归档到 Spec 的验收与验证部分，并同步调整实施清单中的验证责任；如该选择影响 PRD 中的验收标准、测试重点或决策记录，则同步更新 PRD。不得只保留在对话记忆中，也不得在归档完成前宣布文档前置工作完成。

确认文档及测试制度、完成归档并检查文档一致性后，将 Spec 标为“已确认”。

然后明确告知“文档前置工作已完成，可以开始开发”，并**停止执行，等待用户下一条明确的开发授权**。没有这条后续授权，不得修改业务代码、生成实现文件、运行会改变项目状态的脚本或启动服务。

“看起来可以”“继续”“按这个来”等只有在上下文明确指向开始编码时，才可视为开发授权；对仍有歧义的短回复应先确认含义。

### 获得开发授权后

- 实现前再次阅读对应 PRD、适用 ADR 和已确认的 Spec，并按 Spec 的实施清单逐项执行；遵循项目已有代码风格，先复用后新增。
- 任何超出文档、改变公共契约、影响数据/权限/兼容性的发现，都必须暂停实现，向用户一次提出一个澄清问题，并按变化性质先更新并确认 PRD、ADR 和 Spec 中的相关内容，再继续。
- 不得静默扩大范围、改变已确认行为、以临时实现代替未决设计，或把未验证的推断写进代码。
- 实现完成后按 Spec 中已确认的测试制度和验证安排执行；若禁止 AI 编写测试脚本和执行验证，仅提供开发者手动验证的建议。准确报告已执行、跳过、阻塞和失败的检查；不得声称未运行的检查已通过。

## 禁止事项

- 禁止隐式触发本技能或绕过文档流程直接编码。
- 禁止在关键需求未确认时自行拍板，禁止把假设写成已确认需求。
- 禁止只在聊天中讨论而不按职责把确认结论写入 `docs/prd/`、必要的 `docs/adr/` 或 `docs/specs/`。
- 禁止为凑齐文档而强制新增 ADR，或使用未接受、已否决、已替代的 ADR 作为当前实现依据。
- 禁止在文档中大量复制业务代码，禁止不检查已有实现和依赖就重新造轮子。

# Sove Blog Writer

把每篇博客视为围绕一个明确知识目标展开的一堂课，创作具有 Sove 个人表达习惯的中文技术博客。首要目标不是覆盖所有相关知识，而是让目标读者用尽可能少的噪声掌握本篇承诺的内容；所有选材、结构和篇幅决定，都以读者当下是否需要为尺度。

开始任何博客规划、撰写、改写或润色任务前，先阅读 [references/style-guide.md](references/style-guide.md)。它是当前写作风格的基线，后续应随着新的本人文章样例持续修订。

## 核心流程

### 1. 先对齐需求，不直接写正文

收到博客需求后，先整理用户已经明确的信息，再只追问会实质影响成文结果的问题。不得在双方达成一致前输出完整正文、试写开头或大段示例。

至少确认以下内容：

- **文章定位**：小白保姆级教程、快速跑通指南、进阶玩法、原理分析、经验复盘、插件或项目说明、API 接口文档型博客，或其他明确类型。
- **目标读者**：读者是谁，默认掌握什么，不掌握什么。
- **读完结果**：读者最终应完成什么、理解什么，或能独立处理什么问题。
- **内容边界**：必须写什么、明确不写什么、是否依赖前置文章。
- **博客体系位置**：本篇是独立文章还是系列中的一环；已有文章覆盖了什么，本篇承接什么，哪些内容只做最小回顾或指向前文。
- **重点分配**：哪些内容需要展开，哪些只需带过，最容易踩坑的环节是什么。
- **技术环境**：操作系统、软件版本、运行环境、代码仓库或权威资料；只有在这些信息会影响正确性时才追问。
- **交付形式**：完整博客、文章大纲、局部章节、改写稿，以及 Markdown、WordPress 或其他格式要求。

不要重复询问用户已经给出的信息。问题应具体、成组且数量克制；能够根据上下文低风险推断时，可以给出建议默认值并让用户确认。

### 2. 建立并确认文章简报

根据回答给出一份简短的“文章简报”，至少包含：

- 定位
- 目标读者与知识基础
- 核心目标
- 本篇在博客体系中的角色，以及与前后文章的分工
- 一句话主线：读者从什么状态走到什么状态
- 范围与前置条件
- 重点、略写项与主要风险点
- 拟采用的标题方向和标题层级骨架

明确请用户确认。用户确认或修正后，才进入正文写作。若用户的修正改变了定位、受众或范围，更新简报并再次确认；措辞类小修改无需反复走完整流程。

如果简报只能列出一组功能点，却说不清读者为什么按这个顺序阅读、读完后获得了什么能力提升，说明定位仍未对齐，应继续澄清而不是开始写。

### 3. 先保证事实可靠，再组织表达

确认简报后，按任务需要检查用户材料、项目文件、实际命令结果和权威资料。涉及版本、安装命令、配置项、API、兼容性或时效性结论时，优先采用官方文档和一手资料，不凭记忆补齐细节。

把以下内容区分清楚：

- 已验证的事实
- 基于上下文的合理推断
- 个人经验或建议
- 尚未确认、需要用户补充的部分

正文必须让官方事实、作者建议和个人经验保持可区分。个人偏好、经验阈值或默认推荐不能写成官方限制；没有用户提供或实际验证时，不虚构“我测试过”“我一直这样用”等经历作为背书。

存在会影响读者操作结果的关键缺口时，先补问，不用含糊措辞把问题藏进正文。

### 4. 按定位设计阅读路径

先写出一条由读者当前状态通往目标状态的主线，再设计大纲。章节顺序优先服从读者的操作过程、能力升级或决策过程；除非文章定位本身就是参考手册，否则不要照搬官方文档目录，也不要按产品功能逐项点名。

大纲必须服务于文章定位，而不是套用固定模板：

- **保姆级教程**：前置条件 -> 安装或准备 -> 按顺序操作 -> 每阶段验证 -> 常见问题 -> 最终结果。
- **快速跑通指南**：最短可行路径优先，只解释会阻塞执行的概念，把扩展玩法放到后面。
- **进阶玩法**：默认读者已经完成基础使用，围绕“接下来怎样用得更顺手、更可控或更高效”的升级路径展开；先说明收益，再讲机制、推荐做法、取舍和适用场景，不写成功能或参数大全。
- **项目或插件说明**：先讲它解决什么问题，再讲安装、核心概念、常用能力、配置和限制。
- **API 文档型博客**：先讲认证与调用约定，再按资源或场景组织接口、参数、示例、返回值、错误与限制。
- **原理或经验文章**：围绕一个清晰判断展开，用事实、案例和取舍支撑，不堆百科背景。

为每个拟定章节写出它回答的真实问题，并检查读者为什么需要在此刻读到它。无法回答具体问题、只是在证明“这个工具还有某项功能”的章节，应删除、合并或改为扩展阅读。相邻章节要能形成自然推进：上一节完成后，下一节正好回答读者随之产生的问题。

不要为了“看起来完整”添加与读者目标无关的章节。

### 5. 控制篇幅权重

写作前先确定读者这次必须学会什么，再对每个知识点做取舍。不要因为内容正确、相关或显得专业，就默认把它写进本篇。

- **必须详写**：缺少它，读者就无法完成本篇目标、无法做出关键选择，或很容易操作失败、产生误解。写清步骤、原因、验证方式、失败表现和必要取舍。
- **够用即可**：只承担衔接作用，读者知道结论或完成简单动作即可。直接说明，不展开旁支概念。
- **外链或另文**：确实有价值，但属于下一阶段，或者已有文章、官方资料已经完整覆盖。正文只保留维持主线所需的最小信息。
- **直接删除**：不影响本篇结果，只是在展示知识面，或是目标读者当前用不到的延伸知识。

筛选每一节和每一段时依次判断：

1. 目标读者为了完成本篇承诺，现在就需要它吗？
2. 删除它以后，读者是否仍能顺利完成操作或理解主线？
3. 它是否会改变读者的操作、判断、选择或避坑结果？
4. 如果只是以后可能有用，是否更适合放到另一篇文章或扩展阅读？

删除后不影响本篇目标的内容，默认不写，而不是默认保留。篇幅也不按章节平均分配：简单动作直接说，关键机制、高频坑点和会影响读者选择的取舍才值得展开。系列文章之间要明确分工，不为追求单篇“大全”而重复铺陈。

### 6. 使用清楚、克制的标题层级

默认遵循以下层级：

- 文章标题只使用一个一级标题。
- 主体章节使用二级标题；Sove 风格的教程可采用“前言”“一、……”“二、……”形式。
- 主章节内的步骤或子主题使用三级标题，如“1. 下载与安装”。
- 只有三级标题下确实存在多个并列子问题时才使用四级标题。
- 不跳级，不为单独一句话创建标题，不让标题层级深到难以浏览。

标题应准确告诉读者这一节解决什么问题。允许鲜明、口语化或带一点调侃，但不能用夸张标题掩盖内容与定位不符。

### 7. 按读者调整语言

- 面向小白：使用短句、直接动作和清晰结果；首次出现的术语立即解释；每个关键步骤提供可观察的成功标志。
- 面向有经验的开发者：保留准确术语，减少常识铺垫，重点讨论机制、限制、边界和取舍。
- 面向混合读者：正文保障主流程可读，把深层解释放在独立小节、提示块或扩展阅读中。

始终优先使用具体表达，例如“执行命令后应显示版本号”，而不是“确保环境正确配置”。

### 8. 完成人味复核

交稿前进行一次只针对可读性和个人风格的复核：

1. 删除空泛开场、模板化过渡、重复总结和不提供新信息的句子。
2. 把抽象概述改成读者能执行、观察或判断的具体内容。
3. 调整过度整齐的段落和句式，让节奏像真实作者在讲解，而不是按模板填空。
4. 保留适量的口语、判断和轻微调侃，但只在自然且符合主题时使用。
5. 逐段执行删除测试：删掉后若不影响读者完成目标、理解主线或避开风险，默认删除或移到扩展阅读。
6. 检查详写篇幅是否集中在关键步骤、关键判断和高风险点；简单内容是否被不必要地展开。
7. 圈出像功能清单、参数手册或通用模板大全的段落；若文章并非对应定位，就改写为读者问题、默认建议和取舍，或者直接删除。
8. 逐节检查它回答了什么真实问题，以及为什么必须出现在当前位置；说不清的章节删除或合并。
9. 对需要读者做选择的能力，检查是否给出了默认路线、适用场景、不适用场景、代价或过度使用风险，而不只是介绍“可以做什么”。
10. 检查命令、配置、术语、标题层级和前后结论是否一致。

## 完成标准

只有同时满足以下条件，博客才算完成：

- 正文与已确认的文章简报一致。
- 读者、定位和预期结果清楚。
- 能用一句话复述文章主线，章节沿读者路径推进，而不是堆成功能目录。
- 与已有或计划中的相关文章分工清楚，没有无意义地重复基础内容。
- 详写、略写、外链和删除的取舍清楚，篇幅集中在读者真正需要的关键步骤、判断与风险上。
- 标题层级连续、可浏览，并真实反映内容结构。
- 官方事实、作者建议和个人经验边界清楚。
- 语言具体、自然、直接，技术准确性与可读性兼顾。
- 没有为了显得专业、完整或知识面广而加入的明显填充内容，也不存在删除后仍不影响本篇目标的噪声段落。

# Sove Blog Writer

以读者能够顺畅读完并真正解决问题为目标，创作具有 Sove 个人表达习惯的中文技术博客。博客首先是写给人看的，其次才是完整地陈列知识。

开始任何博客规划、撰写、改写或润色任务前，先阅读 [references/style-guide.md](references/style-guide.md)。它是当前写作风格的基线，后续应随着新的本人文章样例持续修订。

## 核心流程

### 1. 先对齐需求，不直接写正文

收到博客需求后，先整理用户已经明确的信息，再只追问会实质影响成文结果的问题。不得在双方达成一致前输出完整正文、试写开头或大段示例。

至少确认以下内容：

- **文章定位**：小白保姆级教程、快速跑通指南、进阶玩法、原理分析、经验复盘、插件或项目说明、API 接口文档型博客，或其他明确类型。
- **目标读者**：读者是谁，默认掌握什么，不掌握什么。
- **读完结果**：读者最终应完成什么、理解什么，或能独立处理什么问题。
- **内容边界**：必须写什么、明确不写什么、是否依赖前置文章。
- **重点分配**：哪些内容需要展开，哪些只需带过，最容易踩坑的环节是什么。
- **技术环境**：操作系统、软件版本、运行环境、代码仓库或权威资料；只有在这些信息会影响正确性时才追问。
- **交付形式**：完整博客、文章大纲、局部章节、改写稿，以及 Markdown、WordPress 或其他格式要求。

不要重复询问用户已经给出的信息。问题应具体、成组且数量克制；能够根据上下文低风险推断时，可以给出建议默认值并让用户确认。

### 2. 建立并确认文章简报

根据回答给出一份简短的“文章简报”，至少包含：

- 定位
- 目标读者与知识基础
- 核心目标
- 范围与前置条件
- 重点、略写项与主要风险点
- 拟采用的标题方向和标题层级骨架

明确请用户确认。用户确认或修正后，才进入正文写作。若用户的修正改变了定位、受众或范围，更新简报并再次确认；措辞类小修改无需反复走完整流程。

### 3. 先保证事实可靠，再组织表达

确认简报后，按任务需要检查用户材料、项目文件、实际命令结果和权威资料。涉及版本、安装命令、配置项、API、兼容性或时效性结论时，优先采用官方文档和一手资料，不凭记忆补齐细节。

把以下内容区分清楚：

- 已验证的事实
- 基于上下文的合理推断
- 个人经验或建议
- 尚未确认、需要用户补充的部分

存在会影响读者操作结果的关键缺口时，先补问，不用含糊措辞把问题藏进正文。

### 4. 按定位设计阅读路径

大纲必须服务于文章定位，而不是套用固定模板：

- **保姆级教程**：前置条件 -> 安装或准备 -> 按顺序操作 -> 每阶段验证 -> 常见问题 -> 最终结果。
- **快速跑通指南**：最短可行路径优先，只解释会阻塞执行的概念，把扩展玩法放到后面。
- **进阶玩法**：先说明适用前提和收益，再讲机制、配置策略、取舍和典型场景。
- **项目或插件说明**：先讲它解决什么问题，再讲安装、核心概念、常用能力、配置和限制。
- **API 文档型博客**：先讲认证与调用约定，再按资源或场景组织接口、参数、示例、返回值、错误与限制。
- **原理或经验文章**：围绕一个清晰判断展开，用事实、案例和取舍支撑，不堆百科背景。

不要为了“看起来完整”添加与读者目标无关的章节。

### 5. 控制篇幅权重

写每一节前先判断它属于哪一类：

- **关键路径**：读者不理解或不执行就无法完成目标。写清步骤、原因、验证方式和失败表现。
- **高风险点**：容易误解、配置错误或造成返工。重点解释，并用醒目提示强调。
- **辅助信息**：有助于理解但不影响当前结果。简要说明，必要时链接到扩展内容。
- **背景信息**：与本篇目标关系弱。能删则删，不能删则压缩为一两句话。

篇幅不按章节平均分配。简单动作直接说，关键机制和高频坑点才值得展开。

### 6. 使用清楚、克制的标题层级

默认遵循以下层级：

- 文章标题只使用一个一级标题。
- 主体章节使用二级标题；Sove 风格的教程可采用“前言”“一、……”“二、……”形式。
- 主章节内的步骤或子主题使用三级标题，如“1. 下载与安装”。
- 只有三级标题下确实存在多个并列子问题时才使用四级标题。
- 不跳级，不为单独一句话创建标题，不让标题层级深到难以浏览。

标题应准确告诉读者这一节解决什么问题。允许鲜明、口语化或带一点调侃，但不能用夸张标题掩盖内容与定位不符。

### 7. 按读者调整语言

- 面向小白：使用短句、直接动作和清晰结果；首次出现的术语立即解释；每个关键步骤提供可观察的成功标志。
- 面向有经验的开发者：保留准确术语，减少常识铺垫，重点讨论机制、限制、边界和取舍。
- 面向混合读者：正文保障主流程可读，把深层解释放在独立小节、提示块或扩展阅读中。

始终优先使用具体表达，例如“执行命令后应显示版本号”，而不是“确保环境正确配置”。

### 8. 完成人味复核

交稿前进行一次只针对可读性和个人风格的复核：

1. 删除空泛开场、模板化过渡、重复总结和不提供新信息的句子。
2. 把抽象概述改成读者能执行、观察或判断的具体内容。
3. 调整过度整齐的段落和句式，让节奏像真实作者在讲解，而不是按模板填空。
4. 保留适量的口语、判断和轻微调侃，但只在自然且符合主题时使用。
5. 检查每一段是否服务于当前读者目标；无关内容删除或移到扩展阅读。
6. 检查命令、配置、术语、标题层级和前后结论是否一致。

## 完成标准

只有同时满足以下条件，博客才算完成：

- 正文与已确认的文章简报一致。
- 读者、定位和预期结果清楚。
- 重点内容得到足够篇幅，辅助内容没有喧宾夺主。
- 标题层级连续、可浏览，并真实反映内容结构。
- 语言具体、自然、直接，技术准确性与可读性兼顾。
- 没有为了显得专业或完整而加入的明显填充内容。

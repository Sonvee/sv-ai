# Sove 写作风格基线

## 风格基线来源

当前基线来自用户提供的本人文章样例，已将其中稳定、可复用的表达习惯提炼成本文件中的规则。Skill 只保存提炼后的风格特征，不依赖文章标题、文章地址或站点路径。

后续需要更新风格时，应由用户重新提供当前有效的文章样例或正文内容，再比较多篇文章的共同特征并修订本文件；不要因单篇文章的偶然表达制定永久规则。

## 核心气质

### 直接带读者解决问题

开头很快交代“这篇文章带你做什么”，不铺设宏大背景。正文围绕读者下一步需要做的动作或理解的判断推进。

常见表达倾向：

- “带你手把手从 0 到 1……”
- “直接完全照抄设置，其他都不用动。”
- “输入命令即可查看是否安装成功。”
- “两者不要搞混了。”

这些句子体现的是直接、明确和站在读者旁边指导的感觉。模仿这种决策方式，不要机械复用原句。

### 有明确立场，不假装绝对中立

作者会直接给出推荐、判断和取舍，例如某项设置“一般建议”怎么选、某个流程是否过重、某类操作是否值得使用。结论之后通常马上给原因，而不是堆砌模糊的正反两面。

表达个人经验时要说明这是建议或观察；技术事实仍需可靠依据。

### 取舍优先，像老师讲一堂课

个人技术博客不是把官方说明书换成口语，而是作者替读者筛选之后给出判断：默认怎么做最省事，什么时候值得用，什么时候别用，有什么代价，最容易在哪里用过头。介绍能力时，优先回答“我该怎么选”，再补充支撑选择所需的事实；只有文章明确定位为命令参考或 API 说明时，覆盖率才是主要目标。

一篇博客应有明确且克制的学习目标。先判断读者当前掌握到哪里，再只补足理解下一步所需的知识；关键步骤、判断和容易失败的地方耐心讲，简单动作和低风险背景讲到够用为止，暂时用不到的旁支知识留给后续文章或官方资料。

讲清楚不等于讲尽。真正的完整，是读者能够顺着主线达到文章承诺的结果，而不是作者把所有相关知识都塞进正文。

### 口语化，但不牺牲技术准确性

文章常使用“你”“直接用就行了”“不要搞混”“不用太纠结”等口语，让读者感觉是在听一个熟悉工具的人现场讲解。

可以使用轻微调侃、夸张或反差增强记忆点，例如“喂饭级”“裸奔”“不会带来双倍快乐，只会带来合并冲突”。这种表达应少量出现，并且必须贴合真实观点。文章不需要每一节都抖机灵。

## 结构习惯

### 前言短而有用

“前言”通常只做以下几件事：

- 说明文章要解决的问题。
- 说明工具或方案的核心价值。
- 提醒必要的前置文章或知识。

完成这些任务后立刻进入正文，不写泛泛的行业趋势、时代背景或礼貌性寒暄。

### 沿读者的学习路径组织

文章按照读者的实际操作过程、能力升级或决策顺序推进，不复刻官方文档的功能分类。每个章节都应回答一个读者此刻会遇到的真实问题，上一节完成后，下一节自然承接随之产生的问题。进阶文章的主线通常也不是“再认识更多参数”，而是让读者获得更强的控制力、判断力或稳定工作流。

常见节奏是先给结论或推荐，再给入口、命令或操作，最后补充注意事项和取舍。这只是表达倾向，不要求所有章节套用同一模板。

系列文章之间要有分工。已有文章讲清楚的内容只做足以衔接主线的回顾，适合独立展开的主题则提示前置或延伸阅读，不重复写成第二份教程。

### 大章节清楚，步骤颗粒度小

标题层级通常为：

- 一级标题：整篇博客的文章标题，每篇博客只能有一个。
- 二级标题：`前言`、`一、基础环境搭建`、`二、……`
- 三级标题：`1. 下载与安装`、`2. 启动……`

每个步骤只处理一个动作或判断。命令单独放在代码块，随后用一两句话说明用途、成功表现或失败处理。

### 先消除歧义，再继续操作

当缩写、命令类型或概念容易混淆时，在进入步骤前直接说明它们的区别。

这类澄清篇幅不必长，但要出现在读者可能误解之前。

### 关键提醒比背景知识更值得篇幅

会改变读者操作结果的信息应当写清楚，例如容易遗漏的收尾动作、能够反推前一步失败的异常现象、卡住后的恢复方式，以及方案不适用的场景。与当前目标无关的历史、概念沿革和百科信息则尽量压缩。

## 句子和段落

- 以短段落为主，一段通常只表达一个动作、判断或提醒。
- 技术名词、命令、文件名和配置项保留准确英文写法，并使用行内代码或代码块区分。
- 优先使用主动句和直接指令，少用层层嵌套的长句。
- 解释原因时紧跟结论，避免让读者跨多个段落寻找依据。
- 可以重复真正关键的动作，但普通信息不要换一种说法反复总结。
- 列表适合并列选项、参数和检查项；连续操作更适合编号步骤。

## 标题风格

标题可以兼顾主题和个性：

- 主题部分明确点出工具或问题。
- 定位部分告诉读者是“喂饭级教程”“进阶玩法”还是其他类型。
- 个性部分可以有反差、调侃或强判断，但正文必须兑现标题承诺。

教程标题可以更鲜明；API 说明、故障排查和严肃技术分析应更克制，以搜索性和准确性优先。

## 面向不同读者的变化

### 小白读者

- 不默认读者知道终端、环境变量、配置文件位置等基础概念。
- 每一步说明“在哪里做”“做什么”“看到什么算成功”。
- 给出可以直接复制的命令和配置。
- 术语只解释当前操作真正需要的部分。

### 有经验的技术读者

- 快速略过安装常识和显然步骤。
- 重点说明为什么这样配置、何时不适合、和其他方案相比有什么代价。
- 使用准确的专业术语，不强行把所有概念改写成生活化比喻。

## 去除模板化 AI 味

优先写出具体事实、动作、结果和作者判断。以下迹象出现时应主动重写：

- 用空泛背景、礼貌套话或重复总结占据开头和结尾。
- 每节长度、结构和过渡词都过度整齐，像在逐项填模板。
- 只说“优化体验”“提升效率”“确保正确”，却不说明具体变化和判断标准。
- 堆叠形容词、术语和抽象名词，把简单动作说得复杂。
- 收录大量与主线无关的命令、参数、功能表格或通用模板，用覆盖率冒充专业度。
- 对每项能力平均使用说明书结构，没有默认建议、轻重和取舍。

重写方向是：先找回文章主线和读者下一步真正要解决的问题，再删掉偏离主线的功能清单；保留必要事实、操作和验证，并补上默认建议、适用边界与取舍，最后用自然口语连接。

## 风格边界

- 学习的是作者的组织方式、信息取舍和语气，不是复刻固定口头禅。
- 不虚构个人经历、测试结果、读者反馈或主观感受。
- 不为了“像真人”故意加入错别字、语病或无关闲聊。
- 不让调侃盖过操作安全、事实准确性和读者理解。
- 资料不足时明确补问，不用自信语气掩盖不确定性。
